## 2. 频道固化：从「名字」到「实体」

### 2.1 现在的问题

频道是每次聚合时按名字临时算出来的 key（`分组 + 归一化名字`）。写法一变就是新频道，
历史全丢，所以无法回答「这条源长期靠不靠得住」。

### 2.2 目标模型（三层）

```
频道目录 channel_registry        长期存在，人工确认过的身份
  └ 频道槽位 cctv-1              稳定 id + 正式名 + 别名 + 分组 + 组内序号
      └ 源档案 channel_source    一条 URL 的归属与人工干预
          └ 健康记录 source_health  每轮结果与历史（沿用 channel_speed_map）
```

存储沿用 KV（与现有 `channel_speed_map` 同构），不新增表；**单 key 超过 5MB 再迁 SQLite 表**。

| KV key | 内容 |
|---|---|
| `live_channel_registry` | `{ id, name, group, order, aliases[], enabled }` |
| `live_channel_order` | 已有：组内顺序 `groups` + 移出规则 `moves` |
| `live_source_overrides` | 人工干预：`{ url: { pin?: number, ban?: true } }` |
| `channel_speed_map` | 已有：每条 URL 的最近结论（速度、失败次数、判定深度、原因） |

### 2.3 归入规则（一次性知识）

```
① channel_id / 正式名完全匹配   → 归入
② 别名表命中                   → 归入
③ 规则归一（CCTV 编号/繁简/后缀）→ 归入，进待确认
④ 编辑距离模糊匹配             → 归入，标低置信
⑤ 全不中                       → 未识别队列
```

未识别队列在「频道」页顶部显示为待办条目，人工点一次归入即写入别名表，**以后不再判断**。
逃生口：新频道 7 天未被确认 → 自动建槽，避免新台被静默吞掉。

## 3. 源健康：四个维度 + 分档排序

| 维度 | 取值 | 来源 |
|---|---|---|
| 可用率 | 近 N 轮成功 / 总轮次（拉普拉斯平滑） | `channel_speed_map` 每轮结果 |
| 延迟 | 首包 p50 | 多采样中位数（已有） |
| 吞吐 | 分片读取速率 KB/s | L2 复验时顺带量（新增） |
| 稳定性 | 失败原因分布 + 抖动 | 失败原因分级（借用 `channel-health` 的思路） |

**排序**：先按可用率分桶（≥0.9 / 0.6~0.9 / <0.6），桶内按综合分；前 3 条仍做域名去相关。
**隔离**：连续 2 轮 L2 失败 → 隔离（保留在列表，不参与优先排序）。
**丢包**：HTTP 层测不到 ICMP 丢包，用「分片成功率 + RTT 抖动」作为代理指标，不宣称是丢包率。

## 4. 「频道」页要有的能力

```
┌ 频道 ────────────────────────────────────────────────────────┐
│ [一键选优]  [保存排序]  [恢复默认]      未识别 12 条 →        │
├ 左：分组 ─────┬ 右：频道 ────────────┬ 源（点频道后展开）─────┤
│ 央视     56  │ 1 CCTV1     18ms ●  │ # 源名   域名    延迟 │
│ 卫视     44  │ 2 CCTV2    210ms ◐  │ 1 南风   120.76… 18ms │
│ 境内地方 281 │ 3 CCTV3    隔离 ○   │ 2 游魂   39.165… 23ms │
│ …            │ …（可拖动）          │ 3 电视… 118.19… 失败 │
└──────────────┴─────────────────────┴───────────────────────┘
源操作：[置顶] [禁用] [删除] [仅保留该域名 1 条]
```

- **手动排序**：沿用现有拖动组件，结果写 `live_channel_order`；
- **删除源**：写 `live_dead_urls`（可回滚），并在「源健康」页可一键恢复；
- **一键选优**：每频道按健康分裁剪到 top N（默认 6 条，可配），保留 `pin`（置顶）与 `ban`（禁用）；
  裁剪结果可回滚——写入前把被裁 URL 记入 overrides 的 `trimmed` 字段；
- **为什么排第一**：展开显示分数构成（可用率 / p50 / 抖动），排序不再是黑盒。

```
┌ 概览 ─────────────────────────────────────────────────────┐
│ 源 16483 · 可用 2814 (17%) · 隔离 1094 · 域名 612          │
├ 视图切换：[按源] [按域名] [按失败原因]                        │
│ 域名             源数  可用率   平均延迟  说明               │
│ 45.192.97.170    487   12%     1820ms   单 IP 挂全集，易崩  │
│ 120.76.248.139   213   68%      240ms                       │
└───────────────────────────────────────────────────────────┘
操作：[隔离该域名] [恢复] [导出清单]
```

「按域名」视图是重点：上一轮实测里 73% 的首位可播率，问题主要出在单 IP 挂几百条的那种源上，
按域名聚合能直接看出谁是瓶颈。

## 6. 分阶段落地

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1** | 输出前复核首位源（每台只测第 1，必要时第 2） | 首位可播率 73% → ≥90%；增量耗时 < 2 分钟 |
| **P2** | 健康档案：speed map 增 `okCount / failCount / p50 / jitter`；分档排序；域名聚合接口 | 排序不再被单次抖动带偏；域名视图可查 |
| **P3** | 频道目录：`live_channel_registry` + 别名表 + 未识别队列 | 同一台在不同源下的写法归入同一 id；未识别可一键归入 |
| **P4** | 「频道」菜单：迁入排序 + 源管理（置顶/禁用/删除/一键选优） | 全部操作可在 UI 完成，且可回滚 |
| **P5** | 「源健康」菜单顶替 MacCMS；MacCMS 前端撤下、后端封存 | 菜单与路由不冲突，点播链路不受影响 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 固化后新频道进不来 | 未识别队列 + 7 天自动建槽；永不静默丢弃 |
| 一键选优误删好源 | 裁剪记录写入 overrides，可一键还原；删除只进黑名单不物理删 |
| KV 单 key 过大 | 超过 5MB 迁 SQLite 表（`source_health`），接口不变 |
| MacCMS 封存影响点播 | 只撤 UI 入口，路由与数据保留；聚合仍读已有 MacCMS 源 |
| 复核首位增加耗时 | 只测每台第 1（必要时第 2），并发 100，预计 1~2 分钟 |
