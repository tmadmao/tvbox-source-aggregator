## 2026-11-08 · 第一轮：跑通与修洞

**做了什么**
- 本地跑通（Node 22 + better-sqlite3），造 `dev/fixture-server.mjs` 夹具，不依赖第三方源做端到端回归。
- 修三个会让测速彻底失效的洞：`url$源名` 未剥离、格式识别用全文 `includes('#EXTINF')`（真实源里有一行命中 → 整份 txt 解析出 0 频道）、默认「按源分开」模式不读测速结果。
- 测速改造：多采样取中位数、TTL 7 天→6 小时、单轮预算 20 分钟、每 300 条增量落盘。
- 新增死源黑名单（含自愈）、频道排序面板（分类 + 拖动 + 央视智能排序）。
- 向上游提了 PR #1。

**为什么**
- 真实源 16022 条 URL，首轮只跑出 3771 可用；排序不生效的根因都在解析层和默认模式，不在排序算法本身。

**踩的坑**
- 夹具最初用 `127.0.0.1`，被 `cleanLocalRefs()` 全部剔除 —— 本地引用对电视端无意义，改局域网 IP 才通过。
- `better-sqlite3` 在 Windows 上预编译可用，没踩编译坑。

**数字**：16022 URL / 8 分钟 / 可用 24%；启动源 3683 频道 / 17515 源。

**做了什么**
- 绿联 NAS 上 Docker 部署（容器 `tvbox-aggregator`，端口 5678）；`dist` 挂载 + `dev/nas-update.sh` 一键更新（约 15 秒）。
- 分组归并从 369 收到 14 个标准组；央视智能排序；购物/推广频道过滤。
- 站点测速与验活合并成一个面板；「不可达剔除」增加「保留链接」选项。
- FTP 对外发布（`http://iptv.new.tg/live.txt`），解决 550：FTP 登录停在 `/`，只有 `/Web` 可写。
- 关闭「配置源自带 lives」——它们挂整份音乐歌单，把「境内专题」灌到 2.3 万条。

**为什么**
- 目标是挂 NAS 后全自动：聚合 → 测速 → 排序 → 生成 txt → 覆盖上传，电视只订阅一个地址。

**踩的坑**
- Alpine 官方源拉 gcc 卡了 9 分钟，换清华源后 90 秒完成。
- 某配置源的「m3u」实际返回 HTML，被按 txt 解析炸出 43 万条垃圾条目，输出一度 11.5MB → 加内容类型闸 + 单源 3 万条上限。
- 频道排序面板在登录前初始化（401）后不再重试，用户一直看到「请先执行聚合」。

**数字**：11 组 / 1089 频道 / 4628 源 / 320KB。

## 2026-11-09 晚 · 第三轮：分片复验与"换基座"的试错

**做了什么**
- 实测「排第一的源」到底能不能播：80 个频道采样，**66% 可播**；其中 23% 是「列表 200 但分片 404/超时」。
- 顺带发现 31% 的多源频道前三条源在同一域名，会一起挂。
- 实现并验证 L2 分片复验（m3u8 列表可达后再拉 2~8KB 分片）+ 域名去相关。
- 把这两项连同格式识别修复、FTP 发布，移植到朋友分支上做并行验证（NAS 5679）。

**为什么**
- 排序没错，是「测的是清单、不是货物」。CDN 返回的列表可能指向另一台已死的源站。

**踩的坑（重要）**
- 朋友分支是「合并 → 测速 → 再合并」，会重复下载所有源。测速跑完 1.6 万次请求后连接池退化，
  第二次下载整批超时，**`lives` 被清成 0，输出直接变空**。正确顺序是「先测速（用上一轮频道树）→ 再合并一次」。
  本仓库同样的顺序，只是被「下载失败沿用上次」的兜底掩盖了。
- 朋友分支默认采用配置源 lives，第一次跑出 4.9MB / 5.7 万条非电视条目。

**决定**
- **不换基座**。实测同口径下新基座首位可播 87%，而本仓库是 68% —— 但差距来源是 L2（我们已经有了），
  不是因为他的架构。5678 只是还没用 L2 重测过。
- 他的仓库降级为**零件来源**：只取 `channel-health`、`source-cache`、黑名单匹配函数，约 400 行；
  932 行的独立后台、规则引擎、ZIP/镜像模块都不进主干。
- 5679 并行实例停用，目录保留作参考。

**下一步**：修测速顺序 → 清缓存重测验证可播率 → P2 源健康档案。
