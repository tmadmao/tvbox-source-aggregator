## 2026-11-10 凌晨二 · 死源模型改「台账」：撤销剪枝，改为周/月回测

**为什么要改**
- 上一节把黑名单从 49808 剪到 12051，理由是「孤儿永远不会自愈、只会占地方」。
- 用户否掉这个判断，理由更硬：**空间的成本可以忽略，源的历史不能丢**。
  一个 URL 死过几次、什么时候死的、最后一次测是什么时候 —— 这些信息在下次采集外部源时能直接复用，
  避免重复入库、重复测速。删掉等于把档案销毁，下次还得从零判断。
- 所以方向反过来了：**只增不删，靠回测周期管理，而不是靠删除管理**。

**新的数据结构（按 v2 重写 `live_dead_urls`）**
```
{"v":2,"rows":[[url, state, since, probedAt], ...]}
state: 1 待观察 / 2 已判死
since: 判定为死的起点   probedAt: 最后一次回测
```
- 兼容 v1 纯字符串数组（读入按 state=1、时间未知处理），不需要停机迁移。
- 用元组而不是对象，省掉一半体积：49808 条 = 3.64MB（原纯字符串 2.6MB）。
- 单键存不下时再考虑分片或迁表；当前量级远未到 5MB 的红线。

**回测周期（写进 `live-deadlist.ts` 常量）**

| 状态 | 周期 | 含义 |
|---|---|---|
| 活（不在台账） | 6 小时 | 原有规则不变 |
| 待观察 state=1 | **7 天** | 判过死，还在观察期 |
| 已判死 state=2 | **30 天** | 死满一个月，降频但不放弃 |

- 判死条件：`since` 距今 ≥ 30 天，且这次回测仍然是 fail → 转 state=2。
- **判死不等于删除**：每月还会测一次，域名哪天复活能自动捞回输出。
- 回测完只刷新 `probedAt`，不重置 `since` —— 否则永远判不了死。

**代码落点**
- `live-deadlist.ts` 重写：`loadDeadRows / addDeadUrls / removeRecoveredUrls / touchProbed / condemnExpired / ledgerStats`。
- `channel-probe.ts`：回测间隔改为查台账（`state=2 → 30 天`、`state=1 → 7 天`），
  回测后 `touchProbed` 刷新时间；原先「确认死链 24 小时」只对**没进台账**的失败源生效。
- `aggregator.ts`：删掉剪枝调用，改为聚合前执行 `condemnExpired`（死满月转判死）。
- `channel-probe-admin.ts`：删掉 `prune-dead` 接口，换成 `GET /admin/channel-probe/ledger`
  （返回待观察/判死/树内待测/体积/域名 Top15）。

**数据修复**
- 上一节删掉的 37757 条孤儿已按新模型放回：`state=2`（判死）、`since` 回填为 30 天前，
  不占输出、不影响过滤，只在档案里躺着。
- 仍在树里的 12051 条：`state=1`，`since` 从本次开始计时，30 天后才会转判死。
- 迁移后校验：台账 49808 / 待观察 12051 / 判死 37757 / 树内待测 0（没有触发补测风暴）。

**验证**
- 聚合正常：1148 频道 / 2525 源 / 全死率 33.2%；南京前六首位仍全部可播。
- 与改造前对比只差 23 个频道，来源是源本身的进出（每轮 site-diff 都有几十条增减），不是台账引入的回归。

**代价（要认）**
- 死链的周回测意味着：**误判一条源，最多一周才会被自动纠正**。
  现有 `POST /admin/channels/reprobe` 可以手动破例立刻重测，重点频道误杀时用它。

## 2026-11-10 凌晨 · 收工后补两件事：日志倒序 + 死源黑名单剪枝

**1. 日志改成倒序（工程习惯）**
- 用户指出：日志正序写，查「最近发生了什么」要滚到底，习惯不对。
- 已按「最新在最上面」重排全文（8 轮 + 评审），《文档索引》加规矩 7；
  「待办速查」作为附录永远放最后。此后新写的一节插在最上面。

**2. 死源黑名单：先查构成、再做机制，不是「写个脚本筛一遍」**

> **已被下一节推翻**：剪枝模型假设「孤儿没有价值」，用户指出源的历史比空间值钱。
> 现改为台账（只增不删 + 周/月回测），此处保留作为决策过程的记录，不要照着实现。
- 构成（实测 49808 条）：
  - **37757 条（75.8%）是孤儿**——URL 已经不在任何源里；
  - 12051 条仍在频道树里，仍在过滤输出。
- 关键认识：孤儿永远不会进测速（不在树里了），也就**永远走不到自愈那条路**，
  只能永久占位。实测其中 37755 条连测速记录都没有。
- 撑大名单的是单个域名：`em.21dtv.com` 32753 条，占全名单 66%。
- 做法（做成机制，否则过几天又长回来）：
  - `pruneUnreferencedDeadUrls()`：每次聚合按「是否仍被频道树引用」剪枝；
  - `POST /admin/channel-probe/prune-dead`：可手动跑一次并返回前后条数；
  - 「清理死源」按钮收紧为**连续两轮失败**才写黑名单（单轮抖动不再误杀整台）。
- 结果：49808 → **12051**（删 37757），KV 从 2.6MB 降到 933KB；
  输出无变化——1171 频道 / 2548 源 / 全死率 32.5% / 南京前五不变。
- 剩余 12051 条与测速结论完全一致（全部 kind=fail），会随 24 小时回测自然消长；
  想再快，就做「死链回测分级」（已列入《开发计划》§3）。

## 2026-11-09 深夜 · 第七轮：重点频道编排 + 三项收尾

**用户的要求**
1. 先确认「置顶/禁用、未识别确认、健康分排序」三项有没有现成资产；
2. 央视和卫视要精细化排序（哪怕手动识别）；
3. 境内地方里找南京地方台、特别是「十八频道」，找到就放最上面；其余地方台不用管。

**资产盘点（先查再动手）**
- 置顶/禁用：**没有**，`channels-admin.ts` 里只有一句「留给下一轮，接口先不假装支持」。
- 未识别确认：**半个**。`findUnmapped / assignAlias / POST /admin/channels/assign` 齐全，
  前端只有只读列表，没有归入入口。
- 健康分排序：**没有接上**。`tierOf / scoreOf` 都在，但排序函数 `compareBySpeed` 只比 `speedMs`。

**查出来的真问题：南京的台不是没有源，是被自己的黑名单吃掉了**
- `live_dead_urls` 5 万条里有 48 条南京，包括官方源 `nklive.nbs.cn`。
- NAS 上实测：清单 25ms 返回、分片 64KB/0.11s —— **完全可用**，属于误杀。
- 死源黑名单没有 TTL、没有白名单，一次抖动就永久生效，整组台从此消失。

**做了什么**
- 新增 `channel-curation.ts`（重点频道编排，约 380 行）：
  - 央视按台号 1→17，5+ 跟 5，4K/8K 单列；CCTV+/NEWS/CGTN/数字付费依次收尾
  - 卫视：江苏（本地）打头 → 常看的省级台 → 大湾区/南方/厦门/海峡 → 少数民族与专业卫视
  - 境内地方：南京六台固定前六（新闻综合/十八频道/教科/文旅纪录/少儿/影视），再按「江苏 → 上海 → 浙江 → 广东 → 其余」
  - 名称清洗：剥掉 `[timeout]`/`[net]`/`[失效]` 这类源侧状态前缀
  - 同名异写合并：`CCTV-4 America` / `CCTV4美洲` → `CCTV4美洲`；`江苏·南京十八生活` / `[net] 江苏·南京十八` → `南京十八频道`
  - 错组归位：被源标进「其他」的 `[reset] 南京教科`、`福建海峡卫视` 等捞回正确分组
  - 伪 CCTV 清出：`CCTV9576`、`CCTV杀人案件(韩国恐怖片)` 这类挪到「其他」组尾
- 死源保护：`PROTECTED_HOSTS = ['nklive.nbs.cn']`；写入时跳过，聚合前自动回捞（`purgeProtectedUrls`）
- 置顶/禁用：KV `live_channel_overrides`；频道页每行两个按钮；禁用后仍在后台可见（按目录补占位行），可撤销
- 未识别归入：频道页未识别区加「目标频道 id」输入（datalist 补全全树 id）+ 归入按钮；「忽略」写入 override
- 健康分排序：`compareBySpeed` 改为 tier（0/1/2 档）→ score（差距 ≥0.12 才压过速度）→ 延迟

**验证（离线，用 NAS 上的真实频道树 1.6MB）**
- 央视 70 → 56：合并 13 行重复、清出 4 个伪 CCTV
- 卫视 46 → 45：`中国农林卫视`/`陕西农林卫视` 合并，`福建海峡卫视` 归位
- 境内地方 935 → 926：前六正好是南京六台，第 7 位起是江苏各市县
- 卫视顺序、南京顺序见《开发计划》§1

**踩的坑**
- 频道显示名用的是「合并时第一个遇到的原始名」（`agg.rawName`），不是归一后的名字 ——
  所以 `CCTV-5+体育` 一直在输出里，而不是 `CCTV5+`。编排层只能在输出前补这一刀。
- 合并重复频道时若把 URL 相加，「每台保留 6 条」会被放大成 18 条；改成取各行最大值后截断。

**上线后又踩了一个大的：整轮聚合卡死**
- 现象：日志停在 `dead-list-filtered` 后再不动；`docker stats` CPU 0.01%，
  `/proc/net/dev` 10 秒只涨 21 个包，`tvbox.db` 9 分钟没有写入，连续三次触发都是 20 分钟不结束。
- 排除法：把 `live_head_verify` 置 `false` 跳过后，同一轮 **38 秒**跑完 → 卡点在 `reverifyHeadSources`。
- 先加了两道保险（单条探测 12 秒硬超时、整轮 8 分钟预算），**仍然卡住**，
  说明 worker 根本没走到探测那一步，更像是 host 信号量或 undici Agent 僵死。
  该步暂时保持关闭，留作单独排查（已知问题 #1）。
- 教训：这类「静默卡死」不要再靠「等一会儿」判断，直接看三样东西 ——
  容器 CPU、`/proc/net/dev` 字节数、DB 文件 mtime。三者同时不动就是死锁，不是慢。

**上线结果（NAS 实测）**
- 聚合 37.7 秒完成，11 分组 / 1239 频道 / 196 KB，FTP 已覆盖 `/Web/live.txt`
- 央视 56 台顺序为 CCTV1→17（5+ 跟 5、4K/8K 单列、CGTN 与付费频道收尾）
- 卫视 45 台，江苏卫视第一
- 境内地方 333 台，前六：南京新闻综合、南京十八频道、南京教科、南京文旅纪录、南京少儿、南京影视；
  前四台首条源都是 `nklive.nbs.cn` 官方口（实测清单 25ms、分片 64KB/0.11s）

**下一步**
- 排查 `reverifyHeadSources` 死锁（先补进度日志：每 50 个频道打一行，再决定是信号量还是 undici）
- 编排规则外置到 KV（现在写死在代码里，改卫视顺序要重新发版）
- 死源黑名单复盘误杀率，考虑 TTL

## 2026-11-09 夜 · 第五轮：输出前复核首位源（P1）

**做了什么**
- 新增 `core/live-verify.ts`：写盘前复核每个频道的前 3 条源，第一条不通过就换下一位。
  复用 `probeUrlOnce`，不另写判定；同域并发限 4。
  实测：1166 个频道 / 1273 次请求 / 75 秒，换源 21 个，整台全挂 454 个。
- 分片复验标准从「读 8KB」提到「读 64KB 且吞吐 ≥100KB/s」，规则版本 4。
  依据：83% 的失败是「能开头、播不动」，8KB 判不出来。

**为什么之前可播率上不去**
- 一度以为 73% 是央视组特有的问题（采样前 60 个频道正好全在央视组）。
  全量实测其实只有 59%：问题不在排序，在**判定标准比播放器宽松**。

**踩的坑（两个，都记下来）**
1. 规则版本迁移写错了：把「验过分片」当成永远当前版本，导致 1695 条用旧标准判过的条目
   永远不重判。改成「成功条目必须有版本号，没有就按当前规则重判」。
2. **连接池退化换了个位置发作**：跑完一轮 1273 次探测后，下一轮聚合卡在「站点验活」
   14 分钟不动，重启才恢复。这不是本轮引入的，是「同进程大量短连接探测」的副作用。
   待办：探测用独立 dispatcher/worker，跑完销毁，不污染后续请求。

**下一步**
- 先修连接池隔离，再复测首位可播率（目标 ≥90%）。此前所有可播率数字都在「标准偏松」下得出，需重测。

## 2026-11-09 晚 · 第三轮：分片复验与"换基座"的试错

**做了什么**
- 实测「排第一的源」到底能不能播：80 个频道采样，**66% 可播**；其中 23% 是「列表 200 但分片 404/超时」。
- 顺带发现 31% 的多源频道前三条源在同一域名，会一起挂。
- 实现并验证 L2 分片复验（m3u8 列表可达后再拉 2~8KB 分片）+ 域名去相关。
- 把这两项连同格式识别修复、FTP 发布，移植到朋友分支上做并行验证（NAS 5679）。

**为什么**
- 排序没错，是「测的是清单、不是货物」。CDN 返回的列表可能指向另一台已死的源站。

**踩的坑（重要）**
- 朋友分支是「合并 → 测速 → 再合并」，会重复下载所有源。测速跑完 1.6 万次请求后连接池退化，
  第二次下载整批超时，**`lives` 被清成 0，输出直接变空**。正确顺序是「先测速（用上一轮频道树）→ 再合并一次」。
  本仓库同样的顺序，只是被「下载失败沿用上次」的兜底掩盖了。
- 朋友分支默认采用配置源 lives，第一次跑出 4.9MB / 5.7 万条非电视条目。

**决定**
- **不换基座**。实测同口径下新基座首位可播 87%，而本仓库是 68% —— 但差距来源是 L2（我们已经有了），
  不是因为他的架构。5678 只是还没用 L2 重测过。
- 他的仓库降级为**零件来源**：只取 `channel-health`、`source-cache`、黑名单匹配函数，约 400 行；
  932 行的独立后台、规则引擎、ZIP/镜像模块都不进主干。
- 5679 并行实例停用，目录保留作参考。

**下一步**：修测速顺序 → 清缓存重测验证可播率 → P2 源健康档案。
