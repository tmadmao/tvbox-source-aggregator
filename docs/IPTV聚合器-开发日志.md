## 2026-11-11 · 第八轮：分级保质保量 + 调度可观测 + 单测 + 规则外置 + 镜像

用户拍板：「单源频道补源」不重要，甚至没意义 —— 看电视就只看央视、其次卫视、再次地方台。
要的是**从央视到卫视再到地方台的源质量**：现在每台 8 条，有的台 8 条跑完都播不出来（超时 5 秒换源）。

**1. 先看现状，确认问题不在「排序」**

拉当前 `live.txt` + `/admin/channels` 对照：
央视 45 台里 38 台是 8 条源，但不少是「1 条活 + 7 条死」；卫视 43 台全是 8 条，同样掺死链。
也就是说客户端按 5 秒逐条试，前 8 条里真正能播的可能只有 1 条，剩下 7 次超时 = 35 秒白等。
电视端体验是「8 条都跑完还是黑屏」，根因是**死链占位 + 只复核首位**，不是排序算法。

**2. 把「保量」改成「保可播条数」**

新增 `core/channel-tier.ts`：
- 分档：央视 / 卫视 / 地方台 / 其他；
- 质量分级：grade 0 稳（分片验证 + ≤2.5 秒 + 新鲜 + 健康）、1 可用、2 未证实、3 死；
  **2.5 秒是客户端 5 秒超时的一半**，超过 4.5 秒直接不算保底；
- 前排编排：死链不输出；可播源优先；前 N 条尽量不同域名（单 IP 挂几百条是主要死因）。

新增 `core/source-guarantee.ts`（Step 6.6c）：
- 配额 **央视 6 / 卫视 5 / 重点地方台 2**；
- 不够就从**完整源池**继续翻候选实测（输出只留 8 条，池子往往还有几十条）；
- 只保央视、卫视、南京+江苏、且有 ≥2 条候选的地方台 —— 单源小台不进配额、不进缺口表。

效果（第一次部署后实测）：央视 44 台 / 216 条源 / **0 条死链**，卫视 43 台 / 286 条源 / **0 条死链**，
境内地方 287 台 / 504 条源 / **0 条死链**。旧版那种「1 活 + 7 死塞满 8 条」不再出现。
整轮聚合 4 分 03 秒（含测速 + 保障 + 复核），769 频道 / 1866 源 / 139KB。

**3. 缺口要说人话**

保障阶段跑在「同名合并」之前，同一个 CCTV1 会以 3 种写法各算一台（第一次报出 69 个央视台）。
改成**输出树定稿后重算**：合并、改名、隐藏全死台之后再统计，和电视上看到的数字一致。
缺口表只列央视/卫视（必列）和地方台里「有 ≥2 条候选但都播不了」的台，
`CCTV+2` / `CCTV4美洲` / `CCTV16-4K` 这类整池全死的冷门付费台被点名 —— 它们需要新上游，不是新代码。

**4. #15 调度执行历史与告警**

`run_history` 记录触发方式（cron/manual/probe）、开始、结束、状态、耗时、产出，保留 7 天；
进程被杀留下的 running 超过 3 小时，下次启动自动收尾成「进程中断」——这才是「昨天 5 点跑没跑」的答案。
失败 / 超时 / 超过 26 小时没成功：后台标红 + 可选 Webhook / Telegram 推送（6 小时去重）；
每天 06:30 与启动后 30 秒各做一次漏跑自检。
实测本次记录：`success / 243s / 769 频道 / 1863 源`，日志页逐日条能看到今天 18:47 有一次成功。

**5. #16 单测：42 个用例，0 新依赖**

`scripts/test.js` 用已有的 esbuild 把 `test/*.test.ts` 打成 mjs，再交给 `node:test`。
覆盖 channel-tier（分级/编排/配额）、curation（规则归一/分档/合并/置顶禁用/档位优先级）、
ledger（v1 兼容/幂等/保护域名/判死/统计）、host-health（抽样/状态机/单条不判死）、run-history（裁剪/悬空/漏跑）。
`npm test` → 42 pass。

**6. #17 编排规则外置**

央视/卫视/南京/省份台序、每台保留条数、各档保底条数全部存 KV `live_curation_rules`；
代码里的常量只做缺省与校验兜底。后台「频道 → 编排规则」可直接改，保存后下一次聚合生效，重启不丢。
验收：把卫视改成「江苏→东方→湖南」，`GET /admin/curation-rules` 立刻返回新序，恢复默认也走通。

**7. #18 镜像防回退**

原来 `dist` 是挂载的，镜像里一直是旧代码，容器重建就回退。
改成构建期打包：`Dockerfile` 接 `APP_VERSION` / `APP_COMMIT` 构建参数，打 `<sha>` 与 `local` 两个标签；
`dev/nas-update.sh` 改为「上传源码 → NAS 上 build → compose up --no-build → 校验 /version」。
容器只挂 `data`，开发热更新单独放 `docker-compose.dev.yml`。
实测重建后 `/version` 返回构建时的 commit，和后端日志的 `Build:` 行一致。

**踩的坑**
- **质量报告统计口径错位**：保障跑在合并前，同一频道多种写法被重复计数（69 个央视台）。改成输出树定稿后重算；
- **单次失败不能判死**：输出前复核偶发一次超时就把好源踢出前排。改成连续 2 次失败才 grade 3，单次只降级留观；
- **admin.ts 是模板字符串**：JS 里的 `'\n'` 被提前转义成真实换行，后台脚本直接语法错误。用 `node --check` 逐段校验才发现。

**下一步**
- 冷门央视付费频道缺源：缺口表已点名，补 1~2 个带付费包的稳定上游；
- 告警通道落地：后台填 Webhook/Telegram 并点「发送测试」；
- 各档达标率进执行记录，看趋势而不是单次快照。

## 2026-11-10 凌晨五 · 修死锁 + 隐藏全死台 + 台账上后台 + 每日快照

按上一节的优先级，一口气推了五项（看板 44% → 72%）。

**1. 死锁修好了，原因和之前猜的不一样**

先前判断「worker 没走到探测、是信号量死锁」，加了硬超时也没用，说明判断错了。
真正的卡点是 `withProbeNet` 的收尾动作：**undici 的 `agent.close()` 会等所有在途请求结束**，
只要有一条连接僵死（服务端不回包也不断开），close() 就永远不返回。
而它在 finally 里 —— 于是整轮聚合挂在「收尾」上：没有日志、没有 DB 写入、网络归零。
和观测到的三零现象完全吻合。

修法：`close()` 加 3 秒超时，超时直接 `destroy()` 强制回收。
同时给 `reverifyHeadSources` 补了每 100 台一行的进度日志（以后不会再「静默卡死」）。

顺带发现同一病根的第二个实例：**站点验活走的是全局 fetch 池**，
被前面的探测打散后会爬行（这次实测卡了 18 分钟，每秒几十字节）。
修法：站点测速改用 `netFetch` + 独立池包裹，跑完销毁。

结果：整轮聚合 **107.6 秒**跑完，复核 1187 台 / 换源 13 台 / 1284 次请求 / 59 秒。

**2. 全死频道默认隐藏**

按用户拍板。`live_hide_dead` 默认开，隐藏了 414 个台，
输出从 1166 → **755 个频道 / 2039 条源 / 157KB**，输出里 **0 个全死频道**。
KV 置 `false` 可退回「保留但沉底」。

**3. 台账上后台**

源健康页新增两块：
- 域名台账：树里域名 / 已入档 / 可疑 / 判死 / 覆盖源 / 本周待测 + 域名 Top20 + 「按当前树重建」
- 输出前复核首位源：复选开关（之前这条只能改 KV，用户根本不知道它被关过）

新增接口 `GET/PUT /admin/live-head-verify`。

**4. 每日数据库快照**

之前从没备份过。应用内 cron `30 5 * * *`（聚合 05:00 之后半小时），
走 SQLite 在线备份 API（不锁库），保留 7 份，落在 `data/backup/`。
不依赖 NAS crontab，跟着代码走。

**验证**

- 聚合：107.6s，`head-reverify-done channels=1187 promoted=13 allDead=422 requests=1284`
- 输出：755 频道 / 2039 源 / 全死 0 / 南京前五首位全可播
- 页面：脚本语法检查通过，`/admin/live-head-verify` 返回 `{"enabled":true}`
- 备份：cron 已注册（`[backup] scheduled: 30 5 * * *`），明早 05:30 首次执行

**剩下的（看板 5 项）**
单源频道补源（78.2% 的台只有 ≤1 条源）、调度执行历史与告警、自动化测试、
编排规则外置、镜像防回退。

## 2026-11-10 凌晨三 · 死源治理上升一层：域名台账 + 抽样复验

**为什么再改一层**
- URL 台账解决了「不丢历史」，但没解决「测得太蠢」：
  1859 个域名名下 12352 条源一条都播不出来，却要按 7 天周期逐条回测。
  同一个域名下的源共享一套 CDN/服务器，**整片死就是整片死**，抽几条即可代表。
- 但**不能一刀切**：实测 63 个域名是「部分活」（45.192.97.170 20%、8.138.7.223 6%），
  这类必须继续逐条判。所以域名层只负责「调度」和「整片过滤」，不替单条 URL 下结论。

**域名清单（实测，频道树 2159 个域名）**

| 分类 | 域名数 | 覆盖源 | 处理 |
|---|---|---|---|
| 全死（0 条可播） | 1859 | 12352 | 进台账，抽 3 条周/月复验 |
| 部分活（<50%） | 63 | 2957 | 不碰，仍逐条判 |
| 健康（≥50%） | 239 | 2653 | 不碰 |

其中「名下 ≥2 条源且全死」的 932 个域名进入台账，覆盖 11428 条源；
剩下的 927 个全死域名每条只有 1 条源 —— 单条样本没有代表性，不做域名级判定。

**状态机（`host-health.ts`）**

| 状态 | 周期 | 行为 |
|---|---|---|
| 无记录 | 按 URL 规则（6h） | 全测 |
| 可疑 state=1 | 7 天 | 到期只抽 **3 条**，全失败 → 维持可疑 |
| 判死 state=2 | 30 天 | 名下源**不再输出**，到期抽 3 条；有一条通 → 立即撤销恢复 |

- 可疑满 30 天且抽样仍全失败 → 自动转判死。
- **抽样按哈希均匀取**，不是取前 3 条：同域名下常常是同一路径换参数，取前三条等于只测一个地址。
  实测 1405 条源抽到的是第 525/342/1065 条。
- 样本 <2 条不下结论；只有 1 条源失败的域名永远不判死。

**省了多少**
- 以前：12352 条死源 × 每周一轮。
- 现在：932 个域名 × 3 条 = 2796 条/周；判死后 2796 条/月。
- 量级上是 **4.4 倍**的工作量缩减（周），判死后 **17 倍**。

**代码落点**
- `host-health.ts`（新）：台账读写、配额、抽样、结算、统计。
- `channel-probe.ts`：构造待测队列时按域名收口；跑完按域名汇总战果并结算。
- `aggregator.ts`：判死域名名下源整片不输出（比逐条 URL 台账更省）。
- 接口：`GET /admin/channel-probe/hosts`（台账概览 + Top20）、
  `POST /admin/channel-probe/hosts/reseed`（按当前树重建）。

**验证**
- 离线单测：配额（-1/0/3）、均匀抽样、结算、满月判死、判死后 30 天周期，全部符合预期。
- 线上：reseed 写入 932 个域名 / 覆盖 11428 条源；聚合后 1166 频道 / 2542 源 / 全死率 32.5%，
  南京前六首位仍全部可播，无回归。

**要认的代价**
- 域名级判定是「抽样代表整体」，有极小概率漏掉一个域名下唯一还活着的那条源。
  缓解：判死的域名每月仍抽 3 条；只要有一条通，整域立刻恢复。

## 2026-11-10 凌晨二 · 死源模型改「台账」：撤销剪枝，改为周/月回测

**为什么要改**
- 上一节把黑名单从 49808 剪到 12051，理由是「孤儿永远不会自愈、只会占地方」。
- 用户否掉这个判断，理由更硬：**空间的成本可以忽略，源的历史不能丢**。
  一个 URL 死过几次、什么时候死的、最后一次测是什么时候 —— 这些信息在下次采集外部源时能直接复用，
  避免重复入库、重复测速。删掉等于把档案销毁，下次还得从零判断。
- 所以方向反过来了：**只增不删，靠回测周期管理，而不是靠删除管理**。

**新的数据结构（按 v2 重写 `live_dead_urls`）**
```
{"v":2,"rows":[[url, state, since, probedAt], ...]}
state: 1 待观察 / 2 已判死
since: 判定为死的起点   probedAt: 最后一次回测
```
- 兼容 v1 纯字符串数组（读入按 state=1、时间未知处理），不需要停机迁移。
- 用元组而不是对象，省掉一半体积：49808 条 = 3.64MB（原纯字符串 2.6MB）。
- 单键存不下时再考虑分片或迁表；当前量级远未到 5MB 的红线。

**回测周期（写进 `live-deadlist.ts` 常量）**

| 状态 | 周期 | 含义 |
|---|---|---|
| 活（不在台账） | 6 小时 | 原有规则不变 |
| 待观察 state=1 | **7 天** | 判过死，还在观察期 |
| 已判死 state=2 | **30 天** | 死满一个月，降频但不放弃 |

- 判死条件：`since` 距今 ≥ 30 天，且这次回测仍然是 fail → 转 state=2。
- **判死不等于删除**：每月还会测一次，域名哪天复活能自动捞回输出。
- 回测完只刷新 `probedAt`，不重置 `since` —— 否则永远判不了死。

**代码落点**
- `live-deadlist.ts` 重写：`loadDeadRows / addDeadUrls / removeRecoveredUrls / touchProbed / condemnExpired / ledgerStats`。
- `channel-probe.ts`：回测间隔改为查台账（`state=2 → 30 天`、`state=1 → 7 天`），
  回测后 `touchProbed` 刷新时间；原先「确认死链 24 小时」只对**没进台账**的失败源生效。
- `aggregator.ts`：删掉剪枝调用，改为聚合前执行 `condemnExpired`（死满月转判死）。
- `channel-probe-admin.ts`：删掉 `prune-dead` 接口，换成 `GET /admin/channel-probe/ledger`
  （返回待观察/判死/树内待测/体积/域名 Top15）。

**数据修复**
- 上一节删掉的 37757 条孤儿已按新模型放回：`state=2`（判死）、`since` 回填为 30 天前，
  不占输出、不影响过滤，只在档案里躺着。
- 仍在树里的 12051 条：`state=1`，`since` 从本次开始计时，30 天后才会转判死。
- 迁移后校验：台账 49808 / 待观察 12051 / 判死 37757 / 树内待测 0（没有触发补测风暴）。

**验证**
- 聚合正常：1148 频道 / 2525 源 / 全死率 33.2%；南京前六首位仍全部可播。
- 与改造前对比只差 23 个频道，来源是源本身的进出（每轮 site-diff 都有几十条增减），不是台账引入的回归。

**代价（要认）**
- 死链的周回测意味着：**误判一条源，最多一周才会被自动纠正**。
  现有 `POST /admin/channels/reprobe` 可以手动破例立刻重测，重点频道误杀时用它。

## 2026-11-09 晚 · 第三轮：分片复验与"换基座"的试错

**做了什么**
- 实测「排第一的源」到底能不能播：80 个频道采样，**66% 可播**；其中 23% 是「列表 200 但分片 404/超时」。
- 顺带发现 31% 的多源频道前三条源在同一域名，会一起挂。
- 实现并验证 L2 分片复验（m3u8 列表可达后再拉 2~8KB 分片）+ 域名去相关。
- 把这两项连同格式识别修复、FTP 发布，移植到朋友分支上做并行验证（NAS 5679）。

**为什么**
- 排序没错，是「测的是清单、不是货物」。CDN 返回的列表可能指向另一台已死的源站。

**踩的坑（重要）**
- 朋友分支是「合并 → 测速 → 再合并」，会重复下载所有源。测速跑完 1.6 万次请求后连接池退化，
  第二次下载整批超时，**`lives` 被清成 0，输出直接变空**。正确顺序是「先测速（用上一轮频道树）→ 再合并一次」。
  本仓库同样的顺序，只是被「下载失败沿用上次」的兜底掩盖了。
- 朋友分支默认采用配置源 lives，第一次跑出 4.9MB / 5.7 万条非电视条目。

**决定**
- **不换基座**。实测同口径下新基座首位可播 87%，而本仓库是 68% —— 但差距来源是 L2（我们已经有了），
  不是因为他的架构。5678 只是还没用 L2 重测过。
- 他的仓库降级为**零件来源**：只取 `channel-health`、`source-cache`、黑名单匹配函数，约 400 行；

**做了什么**
